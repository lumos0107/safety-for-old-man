# 얼굴 윤곽 표시 설계 검토

작성 2026-09-30 · 대상 문서 `design/2026-09-30-face-outline-design.md` (참고 `design/개발_경위와_결정_기록.md`)

## 1. 총평

화면 표시용으로 범위를 좁히고, 넘어짐 판단에 쓰지 않으며, 사람 식별을 제외한 방향은 적절하다. 모델 로드 실패 시 얼굴 기능 없이 뜨는 설계, 기존 클라이언트와의 호환도 좋다.

다만 **실제로 얼굴이 잡히는 거리**와 **얼굴 계산 실패가 뼈대 결과를 막는 문제**는 구현 전에 정해야 한다. **2장은 반드시 반영**, 3~4장은 권장, 5장은 검토할 대안이다.

## 2. 반드시 반영할 것

### 2.1 폰이 보내는 해상도로는 얼굴이 거의 안 잡힐 수 있다
- 화면은 프레임을 긴 변 640으로 줄여 보낸다 (`app.js`의 `MAX_SIDE = 640`). 서버가 받는 것은 640×360이다.
- Face Landmarker의 얼굴 탐지기(short-range)는 입력을 다시 128×128 정도로 줄여 본다. 2m 거리에서 얼굴은 640 프레임에서 약 40px, 탐지기 입력에서는 10px 아래가 된다. 설계 3장의 "약 2m 이내"는 낙관적이고, **실제로는 1m 안쪽이어야 잡힐 가능성이 크다.**
- 9장 테스트의 `zidane.jpg`는 1280×720에 얼굴이 크게 찍힌 사진이라 이 문제를 드러내지 못한다.

반영 방법
- `zidane.jpg`를 **긴 변 640으로 줄인 사진**으로도 `FaceModel`·통합 테스트를 한다.
- 실제 폰으로 **거리별(0.5 / 1 / 2m) 인식 여부를 실측**해 README에 적는다.
- 거리가 부족하면 둘 중 하나를 고른다.
  - 얼굴 윤곽이 켜져 있을 때만 전송 해상도를 긴 변 960~1280으로 올린다. 단순하지만 전송량·지연이 는다. (서버 `max_side` 2000, `max_bytes` 1MB 안에 드는지 확인)
  - YOLO가 이미 주는 코·눈·귀 5점으로 머리 영역을 잘라 확대한 뒤 얼굴 모델에 넣는다. 탐지 거리는 늘지만 코드가 늘고, 원본 픽셀 이상의 정밀도는 나오지 않는다.

### 2.2 얼굴 계산이 실패해도 뼈대 결과는 보낸다
- 설계 6장은 "얼굴 계산 중 예외 → 그 프레임은 `server_error`"로 정했다. 화면 표시용 부가 기능의 실패가 넘어짐 판단의 바탕인 **뼈대 결과까지 버리게** 된다.
- "모델 로드 실패 시 얼굴 기능 없이 뜬다"는 같은 설계의 원칙과도 맞지 않는다.

반영 방법
- 얼굴 계산 예외는 잡아서 **뼈대 결과는 그대로**, `faces` 대신 `"face_error": true`를 붙여 보낸다. 로그에는 기존처럼 예외 종류만 남긴다.
- 자세 추론 예외는 기존대로 `server_error`.
- 9장 테스트 "얼굴 함수 예외 → `server_error`"를 "얼굴 함수 예외 → `result`에 `people` 유지 + `face_error`"로 바꾼다.

### 2.3 모델 내려받기를 안전하게 한다
- 내려받다 끊겨 반쪽 파일이 남으면, 이후 매번 로드에 실패해 `face=false`로 **조용히** 뜬다. 원인을 알기 어렵다.
- 공개 저장소이고 보안을 강조하는 과제인데, 실행 중에 받는 파일의 무결성을 확인하지 않는다.
- 인터넷이 안 되는 곳에서는 내려받기가 서버 시작을 붙잡을 수 있다.

반영 방법
- 임시 파일(`face_landmarker.task.part`)로 받고, 끝나면 이름을 바꾼다.
- 설계 문서에 **SHA-256 값**을 적고, 받은 뒤와 로드 전에 확인한다. 다르면 파일을 지우고 `face=false`.
- 내려받기에 **시간 제한**(예: 30초)을 둔다.
- 경고 로그에 원인(내려받기 실패 / 해시 불일치 / 로드 실패)을 구분해 남긴다.
- 테스트는 모델 파일이 없고 받을 수도 없으면 건너뛴다(skip).

## 3. 권장 (성능·구현)

### 3.1 얼굴 모델은 전용 스레드에서 자세와 동시에 돌린다
- 기존 원칙 "모델 호출이 겹치지 않음"(`app.py`의 추론 전용 스레드)은 **같은 모델을 동시에 부르지 않는다**는 뜻이다. 서로 다른 두 모델을 순서대로 돌릴 필요는 없다.
- 얼굴 전용 스레드 하나(`max_workers=1`)를 따로 두면, 두 모델 각각의 원칙은 지키면서 자세(GPU)와 얼굴(CPU)이 동시에 돈다. 프레임당 지연이 **합이 아니라 둘 중 긴 쪽**이 된다.
- JPEG 디코딩은 한 번만 하고 같은 배열을 두 모델에 넘긴다(읽기만 하므로 안전).
- 참고: Windows용 파이썬 MediaPipe는 GPU를 쓰지 않고 CPU로만 돈다. 얼굴 3개면 10~20ms 추정을 넘을 수 있으니 6장대로 실측해 적는다.

### 3.2 색 순서를 바꿔 넣는다
`decode_jpeg`는 BGR 배열을 돌려준다(YOLO 입력용). MediaPipe `mp.Image`는 SRGB(RGB)를 받는다. 변환을 설계 6장에 한 줄 적어 둔다.

### 3.3 필요 없는 출력은 끈다
`output_face_blendshapes=False`, `output_facial_transformation_matrixes=False`를 명시한다. 계산이 줄고, "표정은 계산하지 않는다"는 2장의 제외 범위를 코드에서도 보여 준다. 478점 중 36점만 꺼내고 나머지는 응답·로그에 넣지 않는다는 점도 8장에 적는다.

### 3.4 `frame` 메시지 해석을 바꾼다
지금 `_frame_seq`는 `seq`만 돌려준다. `face` 필드까지 돌려주도록 바꿔야 하므로 기존 프레임 테스트가 영향을 받는다. 구현 계획에 이 변경을 따로 한 단계로 둔다.

### 3.5 `--no-deps` 설치를 재현할 수 있게 한다
- `requirements.txt`로는 패키지 하나에만 `--no-deps`를 걸 수 없다. 주석만 두면 다른 팀원이 `-r requirements.txt`로 설치할 때 빠진다.
- `server/run.ps1` 또는 README에 **설치 명령을 단계별로** 적는다.
- 1안 확인 때 `mediapipe`가 요구하는 `protobuf`·`numpy` 버전이 현재 환경과 맞는지도 본다. 설치 후 `import cv2`가 여전히 `opencv-python`을 가리키는지 확인한다.

### 3.6 가장자리 자르기 (작음)
얼굴이 화면 끝에 걸리면 0~1로 자른 점들이 테두리에 붙어 윤곽이 납작하게 그려진다. 표시용이라 그대로 두어도 되지만 이유를 한 줄 적어 둔다.

## 4. 사생활·발표

- **기본값을 끔으로 한다.** 8장은 "민감하므로 끌 수 있게 한다"는데 7장 기본값은 켬이다. 사생활을 강조하는 과제라 심사에서 지적받기 쉽다. 시연할 때만 켜는 것이 설명과 일관된다.
- **목적을 한 줄 적는다.** 두 문서 모두 "시연용 표시"라고만 적었다. 사생활을 강조하면서 얼굴 윤곽을 그리면 "왜 필요한가?"라는 질문이 나오기 쉽다. 예: "시연 때 인식이 사람에게 제대로 붙는지 한눈에 보여 주기 위함".

## 5. 검토할 대안: 브라우저에서 계산

얼굴 윤곽은 표시만 하므로, 서버 대신 **폰 브라우저의 MediaPipe(JS/WASM)**로 계산할 수도 있다.

| | 서버 계산 (현재 설계) | 브라우저 계산 |
|---|---|---|
| 의존성 충돌(4장) | 해결 필요 | 없음 |
| 서버 지연 | 늘어남 | 없음 |
| 모델 내려받기(2.3) | 서버에서 처리 | 브라우저가 CDN에서 받음 |
| 해상도(2.1) | 640 프레임 | 카메라 원본 해상도 사용 가능 |
| 폰 부담 | 없음 | 오래된 폰에서 느림·발열 |
| 외부 의존 | 없음 | CDN(jsDelivr 등)에서 모델·라이브러리 로드 |

2.1·2.3·3.5의 부담이 크면 이쪽이 더 단순할 수 있다. 서버 계산을 유지한다면 이 표를 설계 문서에 "고려한 대안"으로 남긴다.

## 6. 개발 경위 문서에 반영할 것

- 6장 얼굴 윤곽 항목에 4장의 "목적" 한 줄을 더한다.
- 7장 "아직 남은 것"에 얼굴 기능 확인 항목(거리별 인식, 실측 fps)을 더한다.
- 구현 후 5장의 "서버 테스트 60개" 숫자를 고친다.
