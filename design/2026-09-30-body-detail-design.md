# 관절·몸 세분화 인식 방안과 설계

작성 2026-09-30 · 팀 눈길손길 · 기반 설계 `design/2026-09-29-web-pose-design.md`
검토 방식: 심사 에이전트 2명 → 합의 → 개정, 3회 (기록 `design/2026-09-30-body-detail-review-rounds.md`)

## 1. 목적

지금 뼈대는 17점이라 몸을 거칠게만 나눈다. 사용자 요청은 "관절이나 몸을 좀 더 구분해서 인식"하는 것이다.

**왜 필요한가**
- **시연:** 사람 모양이 자연스러워야 인식이 제대로 붙어 있다는 게 한눈에 보인다. 지금은 머리가 귀에서 어깨로 바로 떨어지고, 목·골반 가운데·발이 없다.
- **다음 단계(넘어짐·휘청임 판단):** 몸통 축(목–골반 가운데), 머리 꼭대기, 발(뒤꿈치·발끝)이 있으면 "몸이 기울었나", "발이 땅에서 떨어졌나", "머리가 발보다 낮은가"를 더 직접 잴 수 있다. 이 문서는 판단 규칙을 만들지 않고 **재료가 되는 점을 늘리는 것**까지만 다룬다.

## 2. 지금 상태 (YOLO11n-pose, COCO 17점)

| 부위 | 있는 점 | 없는 점 |
|---|---|---|
| 머리 | 코, 눈 2, 귀 2 | 머리 꼭대기, 턱 |
| 몸통 | 어깨 2, 골반 2 | 목, 골반 가운데(몸통 축) |
| 팔 | 팔꿈치, 손목 | 손(손가락) |
| 다리 | 무릎, 발목 | 발(뒤꿈치·엄지발가락·새끼발가락) |

화면에서는 부위별 색(얼굴 분홍·몸통 노랑·왼쪽 파랑·오른쪽 주황)으로 그린다. 얼굴 윤곽(턱선)은 브라우저의 MediaPipe로 따로 그리지만, 얼굴이 화면 폭의 약 1/5 이상일 때만 나온다.

## 3. 후보 방안

| | 방안 | 점 수 | 계산 위치 | 새로 생기는 것 | 비용·위험 |
|---|---|---|---|---|---|
| A | **화면에서 가공** — 있는 점으로 목(어깨 가운데)·골반 가운데를 계산하고, 윗팔/아랫팔처럼 마디를 나눠 그림 | 17 + 계산점 | 브라우저 | 몸통 축 (추정) | 가장 쌈. 발·머리 꼭대기는 만들 수 없음. 추정점이라 판단에 쓰기 애매 |
| B | **더 큰 YOLO 자세 모델** (11m/11x-pose) | 17 | 서버 | 없음 (점이 더 정확해질 뿐) | 설정 한 줄. 세분화 요청과는 무관 |
| C | **RTMPose Halpe26** — YOLO가 찾은 사람 상자마다 26점 모델을 돌림 | **26** | 서버 GPU | 머리 꼭대기, 목, 골반 가운데, 발 6점(엄지·새끼발가락·뒤꿈치 ×2) | 모델 1개(56MB)와 `onnxruntime-gpu` 추가. 사람 1명당 약 5ms |
| D | **RTMW 전신** (COCO-WholeBody) | **133** | 서버 GPU | 발 6 + 얼굴 68(턱 포함) + 손 42 | 모델 129MB. 1명당 약 6~7ms. 얼굴·손 점은 멀면 작고 흔들림. 목·골반 가운데는 없음 |
| E | **MediaPipe Pose Landmarker** (브라우저) | 33 | 폰·노트북 | 발끝·뒤꿈치, 손(엄지·검지·새끼), 입꼬리, 3차원 좌표 | 이미 넣어 둔 `vision_bundle.mjs`로 돌릴 수 있음(모델 lite 5.8MB / full 9.4MB / heavy 30.7MB). 폰 부담이 얼굴 윤곽에 더해짐, 여러 사람에 약함, 서버 뼈대와 이중 계산 |
| F | **부위 분할**(DensePose, Sapiens 등) — 픽셀 단위로 팔·다리·몸통 영역 칠하기 | 영역 | 서버 | 부위 면적 | 모델이 무겁고(수억~수십억 매개변수) Sapiens는 비상업 라이선스. 시제품 범위를 넘음 |

손(21점×2)은 MediaPipe Hand Landmarker(7.8MB)로 브라우저에서 따로 잡을 수도 있지만, 가까울 때만 되고 넘어짐 판단에 쓰임새가 적어 이번에는 뺀다.

## 4. 이 PC에서 해 본 실험 (2026-09-30)

RTX 4080 SUPER, `onnxruntime-gpu` 1.23.2, 사람 상자는 YOLO11n-pose가 찾은 것을 그대로 씀. 이미지는 Ultralytics 예제 `bus.jpg`·`zidane.jpg`와 이를 90°/270° 돌린 것(누운 자세 흉내). **표본이 몇 장뿐이라 경향만 본다.** 실험 스크립트는 저장소에 넣지 않았다.

**속도 (1명, GPU)**

| 모델 | 점 | 1명당 |
|---|---|---|
| YOLO11n-pose (지금) | 17 | 영상 전체 약 9ms |
| RTMPose-s Halpe26 | 26 | 약 3~5ms |
| RTMPose-m Halpe26 | 26 | 약 4~5ms |
| RTMW-m 전신 | 133 | 약 6~7ms |

같은 RTMPose-m을 CPU로 돌리면 1명당 약 10ms였다 (GPU를 못 쓸 때의 대비책이 됨).

**서 있는 사람 (bus.jpg)**: RTMPose 26점은 세 사람 모두 26점이 점수 0.4 이상으로 나왔고, 발 6점이 신발 위에 정확히 찍혔다.

**누운 사람 흉내 (bus.jpg의 한 사람을 잘라 돌림)**

| 각도 | YOLO11n-pose 17점 | RTMPose-m 26점 (같은 상자) |
|---|---|---|
| 서 있음 | 전신 정상 | 전신 정상, 발 포함 |
| 90° | 상자가 상반신만 덮음 → **다리 실패**(무릎·발목 점수 0.06~0.29) | 상자 밖까지 **머리~발 전신을 올바르게 잡음** (상자를 1.25배 넓혀 잘라 보기 때문) |
| 270° | **사람을 못 찾음** (옆 사람 조각을 잡음) | 상자가 틀려서 같이 실패 |

**사람 찾기(검출기) 비교** — 같은 장면에서 정답 상자와 겹친 정도(IoU, 1에 가까울수록 좋음):

| 검출기 | 서 있음 | 90° | 270° | 180° |
|---|---|---|---|---|
| YOLO11n-pose (지금) | 0.80 | 0.66 | 0.14 | 0.13 |
| YOLO11m-pose | 0.78 | 0.23 | 0.82 | 0.31 |
| YOLO11m (검출 전용) | 0.76 | 0.84 | 0.85 | 0.00 |
| YOLOX-m (Human-Art 학습) | 0.89 | 0.04 | 0.83 | 0.90 |

**실험에서 배운 것**
1. 26점 모델은 싸다 (1명당 5ms 안팎). 서버 GPU 여유가 충분하다.
2. **누운 사람에서 약한 곳은 점 개수가 아니라 "사람 찾기"다.** 어느 검출기도 모든 각도에서 안정적이지 않았다. 이 문제는 이 문서의 범위(점 세분화)와 따로, 넘어짐 단계에서 다뤄야 한다 (9장).
3. 상자만 맞으면 RTMPose가 YOLO 17점보다 누운 자세에 강했다 (90° 사례).
4. RTMPose 점수는 0~1을 조금 넘을 수 있다(최대 1.11 관찰). 서버에서 0~1로 자른다.
5. `onnxruntime-gpu` 최신판(1.30)은 CUDA 13용이라 이 PC(파이토치 CUDA 12.8)에서 GPU를 못 쓰고 CPU로 조용히 떨어졌다. **CUDA 12용 1.23.2로 고정**해야 한다. `rtmlib` 패키지를 그냥 설치하면 `opencv-contrib-python`(5.0)과 CPU판 `onnxruntime`이 딸려 와 기존 패키지와 충돌했다 → 패키지로 쓰지 않는다 (6장).

## 5. 추천

**C(RTMPose Halpe26 26점)를 서버에 넣고, 화면은 부위를 더 잘게 나눠 그린다.**

- 요청한 "구분"에 가장 직접 답한다: 머리 꼭대기·목·골반 가운데·발 6점이 **실제로 잰 점**으로 생긴다 (A처럼 추정이 아님).
- 넘어짐 단계에 필요한 재료(몸통 축, 발)가 그대로 생긴다.
- 비용이 작다: 사람 1명당 약 5ms, 서버만 바꾸고 폰 부담은 그대로.
- 턱은 26점에도 없다. 턱선은 지금처럼 얼굴 윤곽(브라우저)이 맡는다. 턱·손가락까지 필요해지면 D(133점)를 같은 구조로 **모델만 바꿔** 넣을 수 있게 만든다 (점 배치 이름 `layout`으로 구분).

고르지 않은 것과 이유
- A만: 발·머리 꼭대기를 만들 수 없고 추정점이다. 대신 화면에서 **마디 구분 그리기**(6.4)는 C와 함께 한다.
- B: 점이 늘지 않는다.
- D를 기본으로: 얼굴·손 점은 멀면 흔들리고 이미 얼굴 윤곽이 있다. 목·골반 가운데가 없다. 전송량도 5배다. 나중에 선택지로 남긴다.
- E: 폰 부담이 얼굴 윤곽과 겹치고, 여러 사람에 약하고, 서버 뼈대와 계산이 둘로 갈린다.
- F: 무겁고 라이선스 문제.

## 6. 설계 (C 방안)

### 6.1 서버 처리 흐름

```
JPEG → 디코드 → YOLO11n-pose (사람 상자 + 17점) → RTMPose-m Halpe26 (상자들을 한 번에 묶어 추론) → 26점
```

- 사람 찾기는 지금 YOLO를 그대로 쓴다 (검출기 교체는 9장의 별도 과제).
- 상자마다 잘라내는 방식은 RTMPose 표준을 따른다: 상자 중심·크기 → 1.25배 넓힘 → 가로:세로 192:256 맞춤 → 아핀 변환으로 192×256 잘라냄 → 정규화 → 추론 → SimCC 출력에서 x·y 최댓값 위치로 좌표 복원 → 원본 좌표로 역변환.
- 모델 입력의 batch 차원이 가변이라 **여러 사람을 한 번에** 추론한다.
- 이 전처리·후처리(약 100줄)는 `rtmlib`(Apache-2.0)의 해당 부분을 참고해 **직접 구현**한다 (`server/pose_detail.py`). 이유: `rtmlib`을 설치하면 OpenCV·onnxruntime 충돌(4장), 실행 중 모델 자동 내려받기를 통제하기 어려움. 파일 머리에 출처와 라이선스를 적는다.
- 점수는 0~1로 자른다. 좌표는 지금처럼 0~1 비율로 보낸다.
- 추론은 지금과 같은 단일 스레드 실행기 안에서 YOLO에 이어 순서대로 한다.

### 6.2 통신 규격 변경

`result`에 `layout`을 더한다. 나머지는 같다.

```json
{"type":"result","seq":12,"img_w":640,"img_h":480,"infer_ms":14.2,
 "layout":"halpe26",
 "people":[{"box":[..],"score":0.91,"kpts":[[x,y,c], ... 26개]}]}
```

- `layout`은 `"coco17"` 또는 `"halpe26"`. 없으면 `"coco17"`로 본다 (예전 서버와 호환).
- 화면은 모르는 `layout`이거나 `kpts` 개수가 맞지 않으면 그 사람을 그리지 않고, 상태 줄에 한 번 알린다 (잘못된 번호로 선을 긋지 않게).
- `infer_ms`는 YOLO와 RTMPose를 합친 시간이다.

Halpe26 점 번호: 0~16은 COCO와 같음. 17 머리 꼭대기, 18 목, 19 골반 가운데, 20·21 엄지발가락(왼·오), 22·23 새끼발가락(왼·오), 24·25 뒤꿈치(왼·오).

### 6.3 모델 파일과 의존성

- 모델: `rtmpose-m_simcc-body7_pt-body7-halpe26_700e-256x192` ONNX (약 56MB, OpenMMLab 배포, Apache-2.0).
  - `tools/fetch_models.py`가 OpenMMLab 주소에서 zip을 받아 `server/models/`(gitignore)에 풀고 **SHA-256을 확인**한다. 실행 중 자동 내려받기는 하지 않는다.
  - 기대 해시(ONNX): `26f3a19e61304a600dfb82d1001d41d24343b89fc70a33ffc84657e0b0bf2ecf` (2026-09-30 받은 파일).
  - 서버 시작 때도 해시를 확인한다. 파일이 없거나 해시가 다르면 → 6.5의 대비 동작.
- 의존성: `onnxruntime-gpu==1.23.2` 고정 (CUDA 12용, 4장). `rtmlib`은 설치하지 않는다.
  - Windows에서 onnxruntime이 CUDA DLL을 찾도록 **torch를 먼저 불러온다** (ultralytics가 torch를 불러오므로 `pose.py`에서 YOLO 다음에 onnxruntime을 불러오면 된다). 이 순서를 코드 주석과 테스트로 지킨다.
- 라이선스: YOLO11(AGPL) 상황은 그대로. 추가되는 RTMPose 모델·코드 참고분은 Apache-2.0 — README 라이선스 메모에 한 줄 더한다. 모델 학습 데이터(Body7: COCO·AI Challenger·CrowdPose·MPII·JHMDB·Halpe·PoseTrack)는 수업 시제품 용도로 문제 없다고 보고 README에 적어 둔다.

### 6.4 화면 그리기 (구분을 눈에 보이게)

점 배치(`layout`)마다 선 목록·부위를 `lib.js`에 표로 둔다. `coco17`은 지금 그대로 유지한다.

`halpe26` 선 연결 (OpenMMLab 기본 연결에서 귀–어깨 선을 뺌):
- 얼굴: 코–눈, 눈–눈, 눈–귀
- 머리·목: **머리 꼭대기–목** (머리가 귀에서 어깨로 떨어지던 모양 대신 목으로 이어짐)
- 몸통: **목–왼/오른 어깨, 목–골반 가운데(척추), 골반 가운데–왼/오른 골반**
- 팔: 어깨–팔꿈치(윗팔), 팔꿈치–손목(아랫팔)
- 다리: 골반–무릎(허벅지), 무릎–발목(종아리)
- 발: 발목–엄지발가락, 발목–새끼발가락, 발목–뒤꿈치

색 (지금 규칙을 넓힘 — 사람 기준 왼쪽은 파랑 계열, 오른쪽은 주황 계열):

| 부위 | 색 |
|---|---|
| 얼굴·머리 꼭대기 | 분홍 (지금과 같음) |
| 목·척추·골반 가운데 | 노랑 (몸통) |
| 왼팔 / 오른팔 | 하늘 / 주황 (지금과 같음) |
| 왼다리 / 오른다리 | 파랑 / 진주황 (지금과 같음) |
| **왼발 / 오른발** | **청록 `#2dd4bf` / 빨강 `#f87171`** (새로 추가) |

- 마디 구분: 윗팔·허벅지는 굵게(지금 굵기), 아랫팔·종아리는 조금 가늘게 그려 관절을 사이에 둔 두 마디가 구분되게 한다. 색을 더 늘리면 범례가 복잡해지므로 굵기로 나눈다.
- 범례에 "청록/빨강 = 왼발/오른발"을 더한다. 17점 서버에 붙으면 발 항목을 숨긴다.
- 상태 줄 "사람" 옆에 "관절 26점" 또는 "관절 17점"을 보여 준다 (지금 어떤 모델에 붙었는지 알게).
- 점 표시 기준 점수: 배치마다 따로 둔다 — `coco17` 0.5(지금 값), `halpe26` 0.4 (4장 실험에서 제대로 잡힌 발 점이 0.39~0.64). 실기기로 조정한다.

### 6.5 설정과 대비 동작

- `server/.env`의 `DETAIL=halpe26`(기본) 또는 `DETAIL=off`.
- 26점 모델을 못 쓰면(파일 없음·해시 불일치·onnxruntime 불러오기 실패) **서버는 멈추지 않고 17점으로 동작**한다. 서버 창에 이유와 해결 방법(`tools/fetch_models.py` 실행 등)을 한 번 크게 띄운다. 시연 도중 모델 문제로 아무것도 안 나오는 것보다 17점이라도 나오는 편이 낫다.
- onnxruntime이 GPU를 못 잡고 CPU로 떨어지면 **서버 창에 경고**를 띄운다 (4장처럼 조용히 느려지지 않게). CPU로도 1명당 약 10ms라 동작은 계속한다.
- 준비 완료 로그에 "관절 26점 (RTMPose-m, GPU)"처럼 실제 상태를 적는다.

### 6.6 성능 목표

- 서버 `infer_ms`: 1명일 때 20ms 이하, 3명일 때 30ms 이하 (지금 약 9~10ms).
- 전송: 26점이라 사람당 JSON이 약 1.5배. 폰 fps가 지금보다 눈에 띄게 떨어지지 않아야 한다 (stop-and-wait라 서버 시간 증가분만큼 줄어듦).

### 6.7 테스트

- `pytest`
  - 전처리: 상자 → 중심·크기·1.25배·가로세로비, 아핀 역변환 왕복 오차.
  - 후처리: 가짜 SimCC 배열에서 좌표·점수 복원, 점수 0~1 자르기.
  - 대비 동작: 모델 파일 없음·해시 불일치 → 17점 `layout:"coco17"`, 로그 문구.
  - 실제 모델(파일이 있을 때만): `bus.jpg`에서 26점, 발 점이 발목보다 아래, 머리 꼭대기가 코보다 위, 목이 두 어깨 사이. 90° 돌린 사람에서 전신이 잡히는지 기록(실패해도 테스트 실패로 두지는 않음 — 9장).

## 7. 위험과 대응

| 위험 | 대응 |
|---|---|
| onnxruntime이 조용히 CPU로 떨어짐 | 시작 로그에 실제 실행 장치 표시, CPU면 경고 (6.5) |
| 모델 파일 변조·다른 판 | 받은 뒤·시작 때 SHA-256 확인 (6.3) |
| 26점 모델이 사람 상자 품질에 매달림 | 상자는 지금 YOLO 그대로. 누운 사람 검출은 9장 과제로 분리 |
| 새 점이 틀리게 찍혀 오히려 어색함 | 배치별 점수 기준, 실기기에서 조정. `DETAIL=off`로 즉시 되돌림 |
| 패키지 충돌 (4장) | `rtmlib` 미설치, 버전 고정, `requirements.lock.txt` 갱신 |

## 9. 다음 과제: 누운 사람 찾기

실험에서 누운 사람을 **찾는 단계**가 각도에 따라 실패했다. 넘어짐 단계를 설계할 때 따로 다룬다. 후보:
- 사람이 안 보이거나 상자가 이상할 때 영상을 90°/270° 돌려 한 번 더 찾기 (계산 2~3배)

- 누운 자세가 많은 데이터로 학습된 검출기 비교 — 팀원이 매트에 누운 영상을 직접 찍어 평가 자료를 만든다
