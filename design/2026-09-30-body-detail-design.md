## 1. 목적

지금 뼈대는 17점이라 몸을 거칠게만 나눈다. 사용자 요청은 "관절이나 몸을 좀 더 구분해서 인식"하는 것이다.

**왜 필요한가**
- **시연 (주 목적):** 사람 모양이 자연스러워야 인식이 제대로 붙어 있다는 게 한눈에 보인다. 지금은 머리가 귀에서 어깨로 바로 떨어지고, 목·골반 가운데·발이 없다.
- **넘어짐 단계의 재료 (부차):** 새로 **실측**되는 재료는 머리 꼭대기(머리 높이·방향)와 발 6점(발 방향·디딤 위치)이다. 몸통 축은 지금 17점의 어깨 가운데–골반 가운데로도 잴 수 있다. 목·골반 가운데 실측점이 그보다 안정적인지는 넘어짐 단계에서 비교한다.
- **이번 변경이 하지 않는 것:** 누운 사람을 **찾는** 능력은 좋아지지 않는다 (4장 결론 2, 9장). 판단 규칙도 만들지 않는다.

## 2. 지금 상태 (YOLO11n-pose, COCO 17점)

| 부위 | 있는 점 | 없는 점 |
|---|---|---|
| 머리 | 코, 눈 2, 귀 2 | 머리 꼭대기, 턱 |
| 몸통 | 어깨 2, 골반 2 | 목, 골반 가운데(몸통 축) |
| 팔 | 팔꿈치, 손목 | 손(손가락) |
| 다리 | 무릎, 발목 | 발(뒤꿈치·엄지발가락·새끼발가락) |

화면에서는 부위별 색(얼굴 분홍·몸통 노랑·왼쪽 파랑 계열·오른쪽 주황 계열)으로 그린다. 몸통은 어깨–어깨, 골반–골반, 어깨–골반 네 선의 노란 사각형이다. 얼굴 윤곽(턱선)은 브라우저의 MediaPipe로 따로 그리지만, 얼굴이 화면 폭의 약 1/5 이상일 때만 나온다.

## 3. 후보 방안

| | 방안 | 점 수 | 계산 위치 | 새로 생기는 것 | 비용·위험 |
|---|---|---|---|---|---|
| A | **화면에서 가공** — 있는 점으로 목(어깨 가운데)·골반 가운데를 계산하고 마디를 나눠 그림 | 17 + 계산점 | 브라우저 | 몸통 축 (추정) | 가장 쌈. 발·머리 꼭대기는 만들 수 없음. 추정점 |
| B | **더 큰 YOLO 자세 모델** (11m/11x-pose) | 17 | 서버 | 없음 (점이 더 정확해질 뿐) | 설정 한 줄. 세분화 요청과는 무관 |
| C | **RTMPose Halpe26** — YOLO가 찾은 사람 상자마다 26점 모델을 돌림 | **26** | 서버 GPU | 머리 꼭대기, 목, 골반 가운데, 발 6점(엄지·새끼발가락·뒤꿈치 ×2) | 모델 1개(56MB)와 `onnxruntime-gpu` 추가. 모델만 약 3ms(4명까지 묶어서). 모델 가중치는 Apache-2.0이나 **학습 데이터 일부의 비상업 조건은 미확인** (6.3) |
| D | **RTMW 전신** (COCO-WholeBody) | **133** | 서버 GPU | 발 6 + 얼굴 68(턱 포함) + 손 42 | 모델 129MB. 모델만 약 6ms. 얼굴·손 점은 멀면 작고 흔들림. 목·골반 가운데는 없음. 학습 데이터 조건 미확인 |
| E | **MediaPipe Pose Landmarker** (브라우저) | 33 | 폰·노트북 | 발끝·뒤꿈치, 손(엄지·검지·새끼), 입꼬리, 3차원 좌표 | 이미 넣어 둔 `vision_bundle.mjs`로 돌릴 수 있음(모델 lite 5.8MB / full 9.4MB / heavy 30.7MB). 폰 부담이 얼굴 윤곽에 더해짐, 여러 사람에 약함, 서버 뼈대와 이중 계산 |
| F | **부위 분할**(DensePose, Sapiens 등) — 픽셀 단위로 팔·다리·몸통 영역 칠하기 | 영역 | 서버 | 부위 면적 | 모델이 무겁고(수억~수십억 매개변수) Sapiens는 비상업 라이선스. 시제품 범위를 넘음 |

손(21점×2)은 MediaPipe Hand Landmarker(7.8MB)로 브라우저에서 따로 잡을 수도 있지만, 가까울 때만 되고 넘어짐 판단에 쓰임새가 적어 이번에는 뺀다.

## 4. 이 PC에서 해 본 실험 (2026-09-30)

- 환경: RTX 4080 SUPER, `onnxruntime-gpu` 1.23.2, 실험에만 `rtmlib` 0.0.16을 썼다. 사람 상자는 YOLO11n-pose가 찾은 것을 그대로 썼다.
- 이미지: Ultralytics 예제 `bus.jpg`·`zidane.jpg`, 그리고 이를 잘라 돌린 것(누운 자세 흉내).
- **재현:** `design/eval/body_detail/spike.py`, 전체 출력은 `design/eval/body_detail/spike.log`. 아래 수치는 따로 표시한 것을 빼고 모두 그 로그에서 옮겼다. 표시한 것(†)은 심사 회차에서 심사위원이 잰 값이고 출처는 `2026-09-30-body-detail-review-rounds.md`. 결과 사진은 저장소 밖에 저장된다(저장소는 사진을 올리지 않음).
- **표본이 몇 장뿐이라 경향만 본다.** 같은 측정도 실행마다 1ms 안팎 흔들린다.

**속도 (GPU, 세션을 직접 불러 예열 5회 뒤 50회 평균, 모델 실행만)**

| YOLO11n-pose (지금) — `predict()` 벽시계 시간, 영상 전체 | 17 | 약 9~10ms (세 번 재서 8.8~10.3ms) | — |

- 참고: `rtmlib` 전체(자르기+추론+복원, 사람마다 batch 1) — 1명 5.3ms, 3명 13.5ms.

- **세션 첫 실행:** 이미 GPU를 쓰는 프로세스에서 새 세션은 만들기 75ms + 첫 실행(batch 4) 97ms. 새 프로세스에서 처음 만든 세션의 첫 실행은 CUDA 초기화까지 더해 약 350~370ms †.

**묶음 크기가 바뀔 때 (RTMPose-m, GPU, 세션 직접)** — 사람 수를 1,2,1,2,3,…으로 바꿔 가며 넣으면:
- batch 크기를 사람 수에 맞추면 **크기가 바뀔 때마다 약 61~85ms** 걸렸다. 같은 크기가 이어질 때만 3ms였다.
- **4로 고정해 채워 넣으면** 첫 호출(약 65ms) 뒤로 사람 수와 상관없이 **약 4.3ms**로 일정했다.

**실험에서 배운 것**
1. 26점 모델은 싸다. 단, GPU에서는 **묶음 크기를 고정**해야 한다 (6.1).
2. **누운 사람에서 약한 곳은 점 개수보다 "사람 찾기"다.** 어느 검출기도 모든 각도에서 안정적이지 않았다. 이 문서의 범위(점 세분화)와 따로, 넘어짐 단계에서 다룬다 (9장).
3. **누운 자세에서 RTMPose가 YOLO보다 강한지는 판단 보류.** 전신 사진(bus 90°)에서 RTMPose는 무릎까지는 잡았지만 발은 틀렸다. 상반신만 찍힌 사진(zidane 90°)에서는 상자가 맞았는데도 팔 점을 **높은 점수로 틀렸다.**
4. **틀린 점 가운데 한 부류는 싸게 거를 수 있다.** 잘라낸 영역 밖을 가장자리에 붙인 점(bus 90° 발, zidane 270° 손목·골반)은 SimCC 첫·끝 칸으로 알아볼 수 있다 (6.1). 가장자리가 아닌 확신 있는 오답(zidane 90° 팔)과 상반신 구도의 가려진 하반신은 이 규칙으로 걸러지지 않는다 (7장).
5. RTMPose 점수는 1을 조금 넘는다 → 0~1로 자른다. 이미지 밖 좌표도 높은 점수로 나온다 → 0점 처리한다.
6. `onnxruntime-gpu` 최신판(1.30)은 CUDA 13용이라 이 PC(파이토치 CUDA 12.8)에서 GPU를 못 쓰고 **예외 없이 CPU로 떨어졌다.** CUDA 12용 1.23.2로 고정한다. `rtmlib`을 그냥 설치하면 `opencv-contrib-python` 5.0과 CPU판 `onnxruntime`이 딸려 와 기존 패키지와 충돌했다 → 서버는 `rtmlib`을 쓰지 않는다 (6.1, 6.3).

## 5. 추천

**C(RTMPose Halpe26 26점)를 서버에 넣고, 화면은 부위를 더 잘게 나눠 그린다.**

추천 이유 (중요한 순서)
1. **요청한 "구분"에 가장 직접 답한다 (시연):** 머리 꼭대기·목·골반 가운데·발 6점이 **실제로 잰 점**으로 생긴다. 머리가 목으로 이어지고, 몸통 사각형 안에 척추 선이 생기고, 다리 끝에 발이 붙는다. 지금의 몸통 사각형은 그대로 둔다 (6.4).
2. **비용이 작다:** GPU에서 모델 실행은 사람 4명까지 약 3~4ms(고정 묶음), 서버만 바꾸고 폰 부담은 그대로.
3. **넘어짐 단계의 재료 (부차):** 머리 꼭대기·발이 실측된다 (1장).

알고 가는 약점: 가까이 서서 상반신만 보이는 구도에서는 가려진 골반·무릎이 화면 아래 가장자리에 그려질 수 있다 (4장, 7장). 실기기로 확인한 뒤 대책을 고른다.

턱은 26점에도 없다. 턱선은 지금처럼 얼굴 윤곽(브라우저)이 맡는다. 턱·손가락까지 필요해지면 D(133점)를 같은 구조로 **모델만 바꿔** 넣을 수 있게 만든다 (점 배치 이름 `layout`으로 구분).

고르지 않은 것과 이유
- A만: 발·머리 꼭대기를 만들 수 없고 추정점이다.
- B: 점이 늘지 않는다.
- D를 기본으로: 얼굴·손 점은 멀면 흔들리고 이미 얼굴 윤곽이 있다. 목·골반 가운데가 없다. 전송량도 5배다. 나중 선택지로 남긴다.
- E: 폰 부담이 얼굴 윤곽과 겹치고, 여러 사람에 약하고, 서버 뼈대와 계산이 둘로 갈린다.
- F: 무겁다. Sapiens는 비상업 라이선스다 (C·D의 학습 데이터 조건도 같은 잣대로 6.3에 적음).

## 6. 설계 (C 방안)

### 6.1 서버 처리 흐름

```
JPEG → decode_jpeg (BGR) → YOLO11n-pose (사람 상자 + 17점) → RGB로 뒤집음 → RTMPose-m Halpe26 → 26점
```

- 사람 찾기는 지금 YOLO를 그대로 쓴다 (검출기 교체는 9장의 별도 과제).
- **묶음 크기:**
  - **세션이 GPU(CUDA)를 잡았을 때:** 사람 상자들을 **batch 4로 채워 넣어** 한 번에 추론한다(빈 칸은 0). 4명이 넘으면 4명씩 나눠 돌리고, 마지막 묶음도 4로 채운다. 이유: 크기가 바뀔 때마다 61~85ms가 걸린다 (4장).
  - **CPU일 때:** 채우지 않는다. batch = 사람 수(4명씩 나눔). CPU에는 크기 전환 지연이 없고, 채우면 1명도 4명 값(약 28ms)이 든다.
  - 사람이 0명이면 RTMPose를 건너뛴다.
  - **예열:** 서버 시작 때 실제로 쓸 묶음 크기로 한 번 돌린다(GPU면 batch 4). 새 프로세스의 첫 실행 비용(약 350ms †)과 GPU의 크기 전환 비용(약 65ms)이 첫 프레임에 나타나지 않게 한다. GPU에서는 크기가 늘 4라 예열 뒤에는 전환 비용이 생기지 않는다.
- **전처리·후처리는 `rtmlib`(Apache-2.0) 0.0.16을 참고해 직접 구현**한다 (`server/pose_detail.py`, 약 100줄, 파일 머리에 출처·라이선스). 값은 다음과 같다.

| 단계 | 값 |
|---|---|
| 상자 → 중심·크기 | 중심 = 상자 가운데, 크기 = 상자 가로·세로 × **1.25** |
| 가로세로비 맞춤 | 모델 입력 192×256(가로×세로)에 맞게, 모자란 쪽을 늘림 |
| 잘라내기 | 아핀 변환(회전 0), 192×256, 선형 보간, 이미지 밖은 0(검정) |
| 색 순서 | **RGB.** 서버의 `decode_jpeg`는 PIL로 읽은 RGB를 BGR로 뒤집어 준다(`server/imaging.py`, YOLO용). RTMPose에는 그 배열을 다시 RGB로 뒤집어 넣는다. mmpose 학습 설정이 `bgr_to_rgb=True`이기 때문이다. `rtmlib`은 BGR을 그대로 넣는다(차이는 4장) |
| 정규화 | 평균 (123.675, 116.28, 103.53), 표준편차 (58.395, 57.12, 57.375), RGB 순서 |
| 출력 풀기 | `simcc_x`(384칸)·`simcc_y`(512칸)에서 각각 최댓값 위치, **÷ 2.0**(분할 비율) |
| 점수 | x·y 최댓값의 **평균**. 점수 ≤ 0이면 위치를 무효로 둠 |
| 원본 좌표 복원 | 좌표 ÷ 입력 크기 × 맞춘 크기 + 중심 − 맞춘 크기/2 |

- **점수와 좌표 정리** (순서대로):
  1. **가장자리 점:** `simcc_x`의 최댓값 위치가 0·1·382·383칸이거나, `simcc_y`의 최댓값 위치가 0·1·510·511칸이면 **점수 0**. 잘라낸 영역 밖을 가장자리에 붙인 점이다 (4장 결론 4).
  2. **이미지 밖 점:** 복원한 좌표가 이미지 밖이면(여유 없이, 0 미만 또는 가로·세로 이상) **점수 0**. 4장의 두 사례(0.6%·1.3% 밖, 점수 0.62·0.70)가 여기에 걸린다. 여유를 두지 않는 이유: 이미지 밖 위치는 모델이 보지 못한 곳의 추정이고, 가장자리로 잘라 그리면 틀린 위치가 된다. 귀·손목이 살짝 잘린 사람의 점 하나를 잃는 쪽이 낫다.
  3. 점수는 0~1로 자르고, 좌표는 0~1 비율로 바꿔 0~1로 자른다.
- 추론은 지금과 같은 단일 스레드 실행기 안에서 YOLO에 이어 순서대로 한다.

### 6.2 통신 규격 변경

`result`에 `layout`을 더한다. 나머지는 같다.

```json
{"type":"result","seq":12,"img_w":640,"img_h":480,"infer_ms":14.2,
 "layout":"halpe26",
 "people":[{"box":[..],"score":0.91,"kpts":[[x,y,c], ... 26개]}]}
```

- `layout`은 `"coco17"` 또는 `"halpe26"`. 없으면 `"coco17"`로 본다 (예전 서버와 호환).
- 화면은 모르는 `layout`이거나 `kpts` 개수가 맞지 않으면 그 사람을 그리지 않는다. 표시는 상단 **"관절" 칸에 `?`** 를 띄워서 한다. 올바른 결과가 오면 다시 `26점`/`17점`으로 돌아간다. 알림 칸(`#notice`)은 프레임 결과가 올 때마다 지워지므로 쓰지 않는다. 표시 문자열은 `lib.js`의 순수 함수가 정한다 (6.4, 6.7).
- **`infer_ms` 정의를 바꾼다:** 지금은 YOLO 모델의 순수 추론 시간(`r.speed["inference"]`)뿐이다. 앞으로는 **`predict()` 시작부터 끝까지의 벽시계 시간**(YOLO 전·후처리 + RTMPose 자르기·추론·복원, JPEG 디코드 제외)이다. 같은 방식으로 잰 지금 기준값은 약 9~10ms (4장).
- **배포 순서:** 옛 화면에 새 서버가 붙으면 멈추지는 않지만, 추가된 점 9개가 옛 홀짝 색 규칙대로 다리 색 점으로 찍힌다. 그래서 **화면(GitHub Pages)을 먼저 배포하고 서버를 나중에 바꾼다.**

Halpe26 점 번호: 0~16은 COCO와 같다. 17 머리 꼭대기, 18 목, 19 골반 가운데, 20·21 엄지발가락(왼·오), 22·23 새끼발가락(왼·오), 24·25 뒤꿈치(왼·오). **17~25는 "홀수=왼쪽" 규칙이 맞지 않는다** (6.4).

### 6.3 모델 파일과 의존성

- 모델: `rtmpose-m_simcc-body7_pt-body7-halpe26_700e-256x192` ONNX (약 56MB, OpenMMLab 배포).
- **`tools/fetch_models.py`:**
  - 받는 주소: `https://download.openmmlab.com/mmpose/v1/projects/rtmposev1/onnx_sdk/rtmpose-m_simcc-body7_pt-body7-halpe26_700e-256x192-4d3e73dd_20230605.zip`
  - zip 안에서 **`*/end2end.onnx` 하나만** 읽어 임시 파일에 쓰고, SHA-256을 확인한 뒤 **`server/models/rtmpose-m_halpe26.onnx`** 로 옮긴다(`server/models/`는 gitignore). 다른 파일은 풀지 않는다.
  - 기대 해시(ONNX): `26f3a19e61304a600dfb82d1001d41d24343b89fc70a33ffc84657e0b0bf2ecf` (2026-09-30 받은 파일).
  - 서버는 **그 경로만** 본다. 서버 실행 중 자동으로 내려받지 않는다.
- 서버 시작 때도 해시를 확인한다. 파일이 없거나 해시가 다르면 → 6.5의 대비 동작.
- 의존성: `server/requirements.txt`에 **`onnxruntime-gpu==1.23.2`만** 더한다 (CUDA 12용, 4장). `rtmlib`은 서버 의존성이 아니다.
- **CUDA DLL 불러오기:** 세션을 만들기 전에 `onnxruntime.preload_dlls()`를 **명시적으로** 부른다. torch를 먼저 불러오는 순서에 기대면, 순서가 바뀌었을 때 예외 없이 CPU로 떨어진다.
  - 이 PC에는 `nvidia-*` pip 패키지가 없다. `preload_dlls()`는 torch 판 이름에 `+cu12`가 있을 때 **torch의 `lib` 폴더에서** CUDA·cuDNN DLL을 불러온다. 곧 GPU 동작은 README의 torch 설치 주소(cu128)에 묶여 있다. **torch를 CUDA 13 빌드로 바꾸면 `onnxruntime-gpu`도 함께 바꿔야 한다** — 이 문장을 README 설치 절차에도 둔다.
- **GPU 사용 판별:** `session.get_providers()[0] == "CUDAExecutionProvider"`로 한다. `ort.get_available_providers()`는 쓰지 않는다 — CUDA DLL을 못 찾아도 목록에는 CUDA가 보인다.
- **개발 환경 정리 순서:** 실험 때문에 `.venv`에 `rtmlib`·`tqdm`이 깔려 있다. ① `rtmlib`으로 원본 대조 기준값(6.7)을 만든다 → ② `.venv`에서 `rtmlib`·`tqdm`을 지운다 → ③ `requirements.lock.txt`를 갱신한다. 테스트는 서버 코드가 `rtmlib`을 불러오지 않는지도 확인한다.
- 라이선스:
  - YOLO11(AGPL) 상황은 그대로다.
  - RTMPose 모델 가중치와 참고한 `rtmlib` 코드는 Apache-2.0이다.
  - 학습 데이터(Body7: COCO·AI Challenger·CrowdPose·MPII·sub-JHMDB·Halpe·PoseTrack18) 중 일부는 비상업 연구용 조건으로 알려져 있으나 **미확인**이다. 수업 시제품에는 쓰고, **기업 연계·상용으로 바꿀 때는 YOLO11 AGPL과 함께 다시 검토**한다. README 라이선스 메모에 같은 문장을 둔다.

### 6.4 화면 그리기 (구분을 눈에 보이게)

점 배치(`layout`)마다 선 목록과 **점→부위 표**를 `lib.js`에 둔다. `coco17`은 지금 그대로 유지한다. `halpe26`의 색은 번호 홀짝이 아니라 **번호별 표**로 정한다 (20·22·24가 왼발이라 홀짝 규칙이 거꾸로다).

`halpe26` 선 연결 (26개). **지금의 노란 몸통 사각형을 유지**하고 척추를 더한다. 그래서 목(18)이나 골반 가운데(19)가 기준 점수 아래로 떨어져도 팔다리는 어깨·골반을 통해 몸통에 붙어 있다. OpenMMLab 기본 연결의 목–어깨, 골반 가운데–골반 선은 사각형 변과 거의 겹쳐 뺐다. 귀–어깨 선도 뺐다.

| 부위 | 선 | 개수 | 색 |
|---|---|---|---|
| 얼굴 | 코–왼눈, 코–오른눈, 왼눈–오른눈, 왼눈–왼귀, 오른눈–오른귀 | 5 | 분홍 |
| 머리·목 | **머리 꼭대기–목, 코–목** (얼굴이 몸과 이어지고, 뒷모습이라 코가 없어도 머리 꼭대기–목으로 이어짐) | 2 | 분홍 |
| 몸통 | 어깨–어깨, 골반–골반, 왼어깨–왼골반, 오른어깨–오른골반 (지금과 같음) + **목–골반 가운데(척추)** | 5 | 노랑 |
| 팔 | 어깨–팔꿈치, 팔꿈치–손목 (×2) | 4 | 왼 하늘 / 오른 주황 |
| 다리 | 골반–무릎, 무릎–발목 (×2) | 4 | 왼 파랑 / 오른 진주황 |
| 발 | 발목–엄지발가락, 발목–새끼발가락, 발목–뒤꿈치 (×2) | 6 | **같은 쪽 다리 색** |

(`coco17`은 지금 19개. 얼굴 5 + 귀–어깨 2 + 몸통 4 + 팔 4 + 다리 4.)

점 색: 0~4·17 분홍, 18·19 노랑, 나머지는 위 표의 같은 쪽 부위 색 (20·22·24 왼발 = 왼다리 색, 21·23·25 오른발 = 오른다리 색).

- **새 색을 더하지 않는다.** 발은 위치와 모양(발목에서 세 갈래)으로 구분된다. 범례도 지금 4항목 그대로다. 빨강은 앞으로 넘어짐 경고 전용으로 남긴다.
- 색각 이상: 새 색이 없으므로 대비는 지금과 같다. 지금 있는 오른팔(주황)–오른다리(진주황)가 적록색약 시뮬레이션에서 가까운 문제는 기존 문제로 기록해 둔다 (색차 약 13 †).
- **선 굵기는 지금처럼 하나로 둔다.** 마디 구분은 관절 점이 해 준다. 굵기를 다르게 하면 원근이나 그리기 오류로 보이기 쉽다.
- 상단 상태 칸: "인원" 옆에 **"관절" 칸**을 새로 둔다. 값은 `26점` / `17점` / `?`(알 수 없는 배치, 6.2) / `-`(연결 전). 정지·재연결 때 `resetStats`에서 `-`로 되돌린다.
- **점 표시 기준 점수:** 배치마다 따로 둔다 — `coco17` 0.5(지금 값), `halpe26` **0.4**.
  - 근거: 서 있는 사람에서 제대로 잡힌 점은 0.41 이상(발은 0.62 이상), 가려진 발은 0.2 이하였다 (4장).
  - 하지만 **가려진 골반·무릎은 0.39~0.71까지 나와** 점수 기준만으로는 못 거른다 (상반신 구도, 4장). 기준을 0.5로 올려도 0.70·0.71은 남는다.
  - 그래서 이번에는 0.4로 두고, 실기기에서 상반신 구도를 확인한다(6.7). 어색하면 고를 대책 후보: ① 이미지 아래 가장자리 몇 % 안에 있는 하반신 점(11~16·19~25)을 그리지 않기, ② 같은 사람의 YOLO 17점 점수가 매우 낮은(예: 0.2 미만) 점은 RTMPose 점수도 낮추기. ①은 고정 카메라 전신 화면에서 바닥에 닿은 발을 지울 위험이 있어, 실기기 자료 없이 정하지 않는다.

### 6.5 설정과 대비 동작

- `server/.env`의 `DETAIL=halpe26`(기본) 또는 `DETAIL=off`. 설정은 서버를 켤 때만 읽는다.
- **시작 때 실패** (파일 없음·해시 불일치·onnxruntime 불러오기 실패·**세션 생성 실패·예열 실행 실패**): 서버는 멈추지 않고 **17점으로 동작**한다. 서버 창에 이유와 해결 방법(`tools/fetch_models.py` 실행 등)을 크게 한 번 띄운다. 시연 도중 모델 문제로 아무것도 안 나오는 것보다 17점이라도 나오는 편이 낫다.
- **추론 중 실패:** RTMPose 단계가 예외를 내면(GPU 메모리 부족 등) 그 프레임은 **이미 계산한 YOLO 17점으로 `layout:"coco17"`을 보낸다** (`server_error`로 버리지 않음). 서버 창에 예외 종류를 요약해 알린다(지금의 요약 로그 방식). **연속 5회** 실패하면 26점을 끄고 17점으로 계속한다고 알린다.
- **GPU를 못 잡으면** (`session.get_providers()` 판별, 6.3) 서버 창에 경고를 띄운다. CPU에서는 묶음을 채우지 않으므로(6.1) RTMPose가 1명 약 10ms, 2명 약 16ms, 4명 약 28ms 더 든다 — **사람이 여럿이면 30ms 목표를 넘을 수 있다**고 함께 알린다. 동작은 계속한다.
- 준비 완료 로그에 "관절 26점 (RTMPose-m, GPU)"처럼 실제 상태를 적는다.

### 6.6 성능 목표

- 서버 `infer_ms`(6.2의 벽시계 정의): 1명일 때 20ms 이하, 3명일 때 30ms 이하. 지금 기준값은 약 9~10ms. (GPU 기준. CPU로 떨어진 경우는 목표 밖이며 6.5처럼 경고한다.)
- **사람 수가 1→2→1→3처럼 바뀌어도** 호출마다 위 목표 안이어야 한다 (묶음 고정의 확인).
- 폰: 같은 폰·같은 장면에서 **fps 감소 15% 이내**. 폰에서 재기 어려우면 서버 `infer_ms` 증가 **10ms 이내**로 판정한다.
- 전송: 26점이라 사람당 JSON이 약 1.5배.

    1. 전처리: 같은 이미지 배열과 상자에서 만든 입력 텐서가 `rtmlib` 전처리 결과(RGB로 바꾼 이미지를 넣음)와 최대 절대 오차 1e-3 이내. 기준값은 텐서 전체 대신 채널별 평균·표준편차와 정해 둔 위치의 값들로 저장한다.
    2. 후처리: 같은 모델 출력(`simcc_x`, `simcc_y`, 저장해 둠)에서 복원한 좌표·점수가 `rtmlib` 후처리 결과와 정확히 같다 (장치와 무관).
    3. 끝에서 끝: 이미지는 양쪽 모두 `server.imaging.decode_jpeg`로 읽고, 기준값과 같은 장치(GPU)에서 돌린다. 점수 0.4 이상인 점만 비교하고, 허용치는 **SimCC 2칸(= 맞춘 크기 ÷ 192 px) 이내·점수 ±0.01**. 묶음 크기(4 대 1)와 장치 차이로 1px을 넘는 차이가 정상적으로 나기 때문이다 (1.64px †). 모델 파일과 GPU가 있을 때만 돈다.

  - 대비 동작: 모델 파일 없음·해시 불일치·**세션 생성 예외·예열 예외** → 17점 `layout:"coco17"`과 로그 문구. **추론 중 예외 → 그 프레임 coco17**, 연속 5회 → 26점 끔.

|---|---|

## 9. 다음 과제: 누운 사람 찾기

실험에서 누운 사람을 **찾는 단계**가 각도에 따라 실패했고, 상반신만 보이는 누운 자세에서는 점도 틀렸다. 넘어짐 단계를 설계할 때 따로 다룬다. 후보:
- 사람이 안 보이거나 상자가 이상할 때 영상을 90°/270° 돌려 한 번 더 찾기 (계산 2~3배)
- 직전 프레임의 사람 위치를 이어 쓰기 (추적)
- 누운 자세가 많은 데이터로 학습된 검출기 비교 — 팀원이 매트에 누운 영상을 직접 찍어 평가 자료를 만든다
