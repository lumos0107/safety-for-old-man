# 관절 세분화 설계 — 심사 합의 기록

대상 `design/2026-09-30-body-detail-design.md`. 사용자 요청(2026-09-30): "에이전트 2개를 만들어 심사의 역할을 부여해서 피드백을 받아서 합의를 통해 개선하고 이를 기록, 3번 정도 진행".

## 진행 방식

- **심사위원 A (기술 심사):** 사실 오류, 모델·전처리 설명의 정확성, 성능 근거, 공급망·보안, 의존성, 대비 동작, 규격 호환, 테스트 빈틈, 기존 코드와의 정합성.
- **심사위원 B (과제·사용자 심사):** 요청에 답하는지, 시연 효과, 넘어짐 목적과의 연결, 추천 근거의 공정성, 범위, 화면 표현(색·범례·색각 이상), 운영 절차, 문서의 명확성.
- 한 회차의 흐름:
  1. 두 심사위원이 따로 문서·코드를 읽고, 필요하면 직접 실행해 지적을 낸다 (읽기 전용 — 파일 수정·설치·서버 조작 금지).
  2. 두 사람의 지적을 합친 목록에 **둘 다** 투표한다 (채택 / 수정채택 / 반대). 상대 지적은 근거를 직접 확인한다.
  3. 의견이 갈린 항목은 상대의 이유를 보여 주고 한 번 더 투표한다.
  4. 둘 다 채택(수정채택 포함)이면 **채택**, 둘 다 반대면 **기각**, 끝까지 갈리면 **합의 실패**(작성자가 판단하고 이유를 남김).
- 작성자(Claude)는 채택 항목을 문서에 반영하고, 반영 위치를 아래 표의 "반영" 칸에 적는다. 다음 회차 심사위원에게는 이전 회차의 합의 결과를 알려 같은 지적을 되풀이하지 않게 한다.
- 실행은 Workflow(심사 2 → 투표 2 → 필요 시 재투표 2)로 했다.

## 1회차

### 심사위원 총평

- 심사위원 A (기술 심사): C안 선택과 전체 구조(YOLO 상자, RTMPose 26점, layout 필드, 17점 대비 동작)는 타당합니다. 모델 해시(26f3a19e…)와 ONNX 입출력(가변 batch, simcc_x 384·simcc_y 512)도 실제 파일과 맞습니다. 다만 6.1의 '여러 사람을 한 번에 묶어 추론'을 이 PC에서 재 보니, 사람 수가 바뀔 때마다 약 60ms씩 멈췄습니다. 이대로면 6.6 성능 목표를 넘으므로 개발 전에 설계를 고쳐야 합니다. 그 밖에 CUDA DLL 로딩과 GPU 사용 판별 방법, 직접 구현할 전처리의 색 순서와 상수, 좌우 색 번호 규칙, 4장 수치의 근거 보존을 문서에 명시해야 합니다.
- 심사위원 B (과제·사용자 심사): 사용자 요청("관절·몸을 더 구분해서 인식")에 C안(Halpe26, 실측 점 9개 추가)으로 답하는 방향은 맞고, 대안 표·대비 동작·호환 규격도 잘 갖춰져 있습니다. 걸리는 곳은 네 가지입니다. 첫째, 4장 실험 결론 중 '상자만 맞으면 RTMPose가 누운 자세에 더 강하다'는 문장이 같은 실험의 반례(zidane 90° 회전 사진)를 빼고 좋은 사례 1건만으로 일반화했습니다. 둘째, 넘어짐 판단과의 연결이 실제보다 크게 쓰였습니다. 셋째, 발 색(빨강) 선택과 마디 굵기 구분이 화면 이해를 오히려 떨어뜨릴 수 있습니다. 넷째, README·가상환경 등 운영 절차와 라이선스 기준이 빠졌거나 일관되지 않습니다. 이 네 가지를 문서에서 고치면 개발에 들어가도 됩니다.

### 항목별 내용

#### A1 가변 batch로 묶어 추론하면 사람 수가 바뀔 때마다 약 60ms씩 멈춤

- 제기: 심사위원 A (기술 심사) · 심각도 높음 · 대상 6.1, 6.6, 6.7
- 문제: 6.1은 'batch 차원이 가변이라 여러 사람을 한 번에 추론'한다고 합니다. 그런데 onnxruntime-gpu 1.23.2 CUDA EP에서 이 모델은 입력 batch 크기가 직전과 다를 때마다 첫 실행이 약 60ms 걸립니다. 전에 본 크기로 돌아가도 같습니다. 실제 영상에서는 검출 인원이 프레임마다 1↔2명처럼 자주 흔들리므로 infer_ms가 반복해서 60ms를 넘습니다. 6.6 목표(1명 20ms·3명 30ms)를 지킬 수 없습니다. 게다가 4장의 '1명당 3~5ms'는 rtmlib이 사람마다 batch=1로 돌린 값이라, 묶음 추론 방식은 측정된 적이 없습니다. 세션의 첫 실행도 372ms인데 RTMPose 예열 계획이 없습니다.
- 근거: scratchpad/reviewA_alt.py 실행 결과: batch를 1,2,1,2,3…로 바꿔 가며 돌리면 크기가 바뀌는 매 호출이 56~74ms, 같은 크기가 이어질 때만 2.3~2.7ms였습니다. 4로 고정해 채워 넣으면(패딩) 전 구간 3.2~4.9ms로 안정됐습니다. cudnn_conv_algo_search=HEURISTIC으로 바꿔도 크기 변경 때 60~108ms로 개선되지 않았습니다. 세션 첫 실행은 372ms였습니다(reviewA_batch.py).
- 제안: 6.1을 '고정 batch N(예: 4)으로 채워 넣어 추론하고, N명이 넘으면 N씩 나눠 돌림, 사람이 0명이면 RTMPose를 건너뜀'으로 바꿉니다. 사람마다 batch=1로 도는 방식도 대안으로 적습니다. 서버 시작 때 그 고정 크기로 예열한다는 문장을 더합니다. 6.7에는 '사람 수 1→2→1→3을 번갈아 넣었을 때 호출마다 걸린 시간이 목표 안인지' 보는 성능 테스트를 추가합니다. 4장 속도 표에는 '사람마다 batch=1로 잰 값'이라고 밝힙니다.
- A 투표 (채택): reviewA_alt.py로 직접 확인한 사실이다. batch 크기가 바뀔 때마다 56~74ms가 걸리고, 고정 batch에 채워 넣으면 3~5ms로 안정된다. 6.6 목표를 지키는 데 결정적이고, 4장 속도 수치가 사람마다 batch=1로 잰 값이라는 점도 밝혀야 한다.
- B 투표 (채택): reviewA_alt.py를 다시 돌려 확인했다. batch 크기가 바뀌는 호출은 60~70ms, 같은 크기가 이어질 때만 2.5~3.5ms였다. 4로 고정해 채우면 첫 호출(70ms) 뒤로 3.2~4.1ms로 안정됐다. 사람 수가 흔들리는 시연 장면에서는 6.6 목표를 못 지키므로 문서 수정이 꼭 필요하다. 사람마다 batch=1로 도는 방식도 크기가 늘 1이라 대안으로 맞다.
- **결과: 채택** — 반영: 6.1 묶음 4 고정·예열, 6.6, 6.7, 4장 묶음 표

#### A2 CUDA DLL 로딩을 import 순서에 맡기지 말고, GPU 사용 여부는 session.get_providers()로 판별

- 제기: 심사위원 A (기술 심사) · 심각도 중간 · 대상 6.3, 6.5, 7
- 문제: 6.3은 'ultralytics가 torch를 불러오므로 YOLO 다음에 onnxruntime을 불러오면 된다'고 import 순서에 의존합니다. 순서가 틀리면 onnxruntime은 예외 없이 CPU로 떨어집니다. 이때 ort.get_available_providers()는 여전히 CUDA를 목록에 넣어 보여 주므로, 이 함수로 판별하면 6.5의 CPU 경고가 뜨지 않습니다. onnxruntime 1.23.2에는 이 문제를 위한 공식 함수 onnxruntime.preload_dlls()가 있습니다.
- 근거: torch를 불러오지 않고 세션을 만들면 'cublasLt64_12.dll which is missing' 오류 로그만 남습니다. 이때 get_available_providers()=['TensorrtExecutionProvider','CUDAExecutionProvider','CPUExecutionProvider']인데 session.get_providers()=['CPUExecutionProvider']였습니다. torch 없이 ort.preload_dlls()를 부른 뒤에는 session.get_providers()=['CUDAExecutionProvider','CPUExecutionProvider']였습니다. ultralytics를 먼저 불러온 경우도 CUDA가 정상이었습니다.
- 제안: 6.3에 '세션을 만들기 전에 onnxruntime.preload_dlls()를 명시적으로 호출한다(torch 쪽 DLL을 쓰는 순서 의존은 보조 수단)'를 적습니다. 6.5와 7장에 'GPU 여부는 session.get_providers()[0] == "CUDAExecutionProvider"로 판별한다. get_available_providers()는 쓰지 않는다'를 명시합니다. 6.7에는 torch를 불러오지 않은 새 프로세스에서 GPU가 잡히는지 확인하는 테스트를 넣습니다.
- A 투표 (채택): torch 없이 세션을 만들면 get_available_providers()에는 CUDA가 보이는데 실제 세션은 CPU였다. 6.5의 경고가 뜨지 않는 구체적 결함이다. preload_dlls()가 공식 해법이다.
- B 투표 (채택): .venv의 onnxruntime 1.23.2에 preload_dlls가 있는 것을 확인했다(hasattr=True). import 순서에 기대면 CPU로 조용히 떨어질 수 있다. 판별 함수를 잘못 고르면 6.5의 경고가 뜨지 않으니 문서에 명시할 가치가 있다.
- **결과: 채택** — 반영: 6.3 preload_dlls·판별, 6.5

#### A3 직접 구현할 전처리·후처리의 상수와 색 순서가 문서에 없고, rtmlib 결과와 맞춰 보는 기준 테스트도 없음

- 제기: 심사위원 A (기술 심사) · 심각도 중간 · 대상 6.1, 6.7
- 문제: 6.1은 '정규화'라고만 적었습니다. 재구현에 꼭 필요한 값이 빠져 있습니다: 평균·표준편차(123.675,116.28,103.53 / 58.395,57.12,57.375), 입력 색 순서, SimCC 분할 비율 2.0, 점수=x·y 최댓값의 평균, 점수 ≤0이면 위치를 -1로 두는 처리. 특히 rtmlib은 OpenCV의 BGR 이미지를 RGB로 바꾸지 않고 RGB 순서 평균값으로 정규화합니다. 반면 mmpose 학습 설정은 bgr_to_rgb=True로 알려져 있으므로 원본 설정 확인이 필요합니다. 어느 쪽을 따르느냐에 따라 좌표가 달라집니다. 또 '약 100줄 직접 구현'이 원본과 같게 동작하는지 확인하는 테스트가 6.7에 없습니다.
- 근거: rtmlib/tools/pose_estimation/rtmpose.py의 preprocess에는 cvtColor가 없습니다(rtmlib 전체를 grep해도 BGR2RGB 없음). post_processings.py의 get_simcc_maximum은 _combine_axis_scores(method='mean')를 쓰고, locs[vals<=0]=-1로 둡니다. bus.jpg 3명을 BGR과 RGB로 각각 넣어 비교하니 평균 점수는 0.807 대 0.808로 비슷했지만, 좌표 차이는 평균 0.8px, 최대 20.4px였습니다(reviewA_check.py).
