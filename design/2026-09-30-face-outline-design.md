# 얼굴 윤곽 표시 설계 (브라우저 계산)

작성 2026-09-30 · 팀 눈길손길 · 기반 설계 `design/2026-09-29-web-pose-design.md` (이 문서는 그 위에 얹는 추가 기능)
개정 2026-09-30 · `2026-09-30-face-outline-design-review.md` 반영 — 서버 계산에서 **브라우저 계산**으로 바꿈
2차 개정 2026-09-30 · `2026-09-30-face-outline-design-review-2.md` 반영 — 탐지 거리 근거 정정, CSP, 메인 스레드 부담 등 (끝의 "검토 반영 기록" 참고)

## 1. 목적

폰·노트북 화면에서 사람의 뼈대에 더해 **얼굴 윤곽(턱선·이마 둘레)**을 그린다.

**왜 필요한가:** 시연할 때 인식이 사람에게 제대로 붙어 있는지 한눈에 보여 주기 위한 **표시 기능**이다.
넘어짐·휘청임 판단에는 쓰지 않는다. 판단에 필요한 머리 위치는 자세 모델의 코·눈·귀 5점으로 충분하다.

자세 모델(YOLO11n-pose)은 얼굴에서 5점만 주므로 윤곽을 만들 수 없다. 얼굴 전용 랜드마크 모델이 필요하다.

## 2. 범위

포함
- 브라우저에서 얼굴 랜드마크 모델 실행, 윤곽 36점 그리기
- 설정의 켜기/끄기 (기본 끔), 얼굴 수 표시

제외
- 서버·통신 규격 변경 — **없음.** 서버는 얼굴을 계산하지 않고 얼굴 정보를 받지도 않는다.
- 눈·눈썹·입 모양, 표정·통증 판단, 고개 방향 계산
- 얼굴로 사람을 식별하는 모든 기능
- 얼굴과 사람(뼈대)을 짝짓기 — 화면에 따로 그리기만 한다

## 3. 왜 브라우저에서 계산하나

| | 서버 계산 (처음 설계) | 브라우저 계산 (선택) |
|---|---|---|
| 해상도 | 서버가 받는 640 프레임으로 계산 | 카메라 원본(최대 1280×720)으로 계산해 **윤곽이 더 정밀함.** 탐지 거리는 같음 — 탐지기는 해상도와 상관없이 프레임 전체를 128×128로 줄여 보므로 **화면 속 얼굴 비율**로 정해진다 |
| 얼굴 실패가 뼈대에 주는 영향 | 따로 처리 필요 | 결과는 서버와 별개라 영향 없음. 다만 계산이 화면의 메인 스레드에서 돌아 **느린 폰에서는 뼈대 fps도 떨어질 수 있다** (5장의 상한으로 줄임) |
| 모델 내려받기 안전성 | 실행 중 내려받기·해시 확인 필요 | 저장소에 함께 두어 git이 무결성 보장, 실행 중 외부 내려받기 없음 |
| 서버 지연 | 늘어남 | 없음. 윤곽이 영상에 바로 따라붙음 |
| 설치 | `mediapipe`와 OpenCV 충돌 해결 필요 | 서버 변경 없음 |
| 사생활 설명 | 서버가 얼굴 좌표를 계산 | "얼굴 정보는 서버에서 계산하지 않는다" |
| 부담 | PC | 카메라 기기(폰·노트북). 오래된 폰은 느리거나 뜨거워질 수 있음 |

브라우저 계산을 택한 이유는 서버 무변경, 의존성 충돌 없음, 얼굴 정보가 서버로 가지 않음이다. 탐지 거리는 이유가 아니다 (위 표 해상도 행).

노트북을 카메라로 쓰는 경우도 브라우저 계산이 맞다. 이 모델은 폰에서 실시간으로 돌리도록 만든 가벼운 모델이라 노트북은 GPU 없이도 충분하다. 노트북을 서버로 쓰는 경우에는 GPU가 없어 서버 부담을 줄이는 쪽이 더 중요하다.

## 4. 모델과 파일

- **MediaPipe Face Landmarker** (웹용 `@mediapipe/tasks-vision` 1.0.1, Apache-2.0). 얼굴당 478점 중 **윤곽(face oval) 36점만** 쓴다.
- 윤곽 36점의 순서 (MediaPipe 얼굴 메시 번호, 이 순서로 이으면 닫힌 윤곽선):
  `10, 338, 297, 332, 284, 251, 389, 356, 454, 323, 361, 288, 397, 365, 379, 378, 400, 377, 152, 148, 176, 149, 150, 136, 172, 58, 132, 93, 234, 127, 162, 21, 54, 103, 67, 109`
- 설정: 얼굴 최대 3개, 탐지 신뢰도 0.5, 실행 모드 VIDEO, `outputFaceBlendshapes: false`, `outputFacialTransformationMatrixes: false` (표정·머리 자세는 계산하지 않음).
- 가속: `createFromOptions`를 `delegate: "GPU"`(WebGL)로 먼저 만들고, 실패하면 `"CPU"`로 다시 만든다. 헤드리스 Chrome(자동 테스트)은 WebGL이 없어 CPU 경로로 돌 가능성이 크다 — 자동 테스트는 CPU 경로, GPU 경로는 실기기 수동 시험으로 확인한다.
- 탐지 거리: 탐지기는 가까운 거리(short-range)용이고 **화면 속 얼굴 비율**로 정해진다. VIDEO 모드는 한 번 잡은 얼굴을 다음 프레임부터 이전 윤곽 주변에서 따라가므로, 가까이서 잡은 뒤 물러나면 더 먼 거리까지 유지될 수 있다 (7장 실측). 서버의 머리 5점으로 영상 일부를 잘라 넣어 거리를 늘리는 방법은 코드가 크게 늘어 이번 범위에서 뺀다.
- **파일을 저장소에 함께 둔다** (`vendor/mediapipe/`, Pages가 같은 주소에서 제공). CDN에서 실행 중에 받지 않는다 — 외부 서버 의존과 공급망 위험을 없애고, 파일 무결성은 git 기록이 보장한다.
  - `vision_bundle.mjs` (155KB)
  - `wasm/vision_wasm_internal.js`, `wasm/vision_wasm_internal.wasm` (12MB, WebAssembly SIMD 판)
  - `face_landmarker.task` (약 4MB, float16 모델)
  - 비SIMD 판(11MB)은 넣지 않는다. 라이브러리가 스스로 경로를 고르면 비SIMD 파일을 찾다 404가 나므로, 불러오기 전에 `FilesetResolver.isSimdSupported()`로 직접 확인하고 파일 경로는 SIMD 판으로 **고정**해 넘긴다. 지원하지 않는 오래된 브라우저(iOS 16.4 미만 등)에서는 불러오지 않고 "이 브라우저에서 얼굴 윤곽을 쓸 수 없음"을 띄운다. 뼈대는 그대로 동작한다.
  - 파일의 출처(npm 패키지 주소·버전, 모델 주소)와 SHA-256을 `vendor/mediapipe/SOURCE.md`에 적어 누가 받아도 같은 파일인지 확인할 수 있게 한다.
  - Apache-2.0 재배포 조건에 따라 라이선스 사본 `vendor/mediapipe/LICENSE`를 함께 두고 `SOURCE.md`에서 가리킨다. `.gitattributes`에 `vendor/** linguist-vendored`를 넣어 GitHub 언어 통계에서 뺀다.
- **보안 정책(CSP)**: MediaPipe는 `.wasm`과 `.task`를 **fetch로** 받으므로 `connect-src`에 `'self'`가 있어야 한다 (`connect-src`를 따로 정하면 `default-src 'self'`는 fetch에 적용되지 않는다). WebAssembly 실행에는 `'wasm-unsafe-eval'`이 필요하다. 새 정책:
  ```
  default-src 'self'; script-src 'self' 'wasm-unsafe-eval';
  connect-src 'self' wss: ws://localhost:* ws://127.0.0.1:*; img-src 'self' blob:; media-src 'self' blob:
  ```
  외부 주소는 여전히 허용하지 않는다. 구현 중 추가 완화가 필요하면 이 문서에 이유와 함께 적는다. 아이폰 Safari가 `'wasm-unsafe-eval'`을 받아들이는지는 실기기로 확인한다.
  - (구현 중 발견) MediaPipe는 모델을 만들 때 **사용 통계 기록기**를 붙여 `https://odml.pa.googleapis.com/v1/log`로 보내려 한다. 끄는 옵션이 없다. 이 CSP가 그 전송을 **막는 것이 의도된 동작**이다 — 이 기기 밖으로 아무것도 나가지 않는다. 라이브러리 파일을 고쳐 끄지 않는 이유: 원본 그대로여야 출처·해시 기록이 의미가 있다. 기록기는 모델 인스턴스마다 만들어지고(닫을 때 한 번 더 보내려 함) 한 번 실패하면 그 인스턴스는 다시 보내지 않으므로, 차단 오류는 켤 때·다시 만들 때·GPU→CPU 전환 때마다 한 번씩 난다 (최종 검토에서 정정). 보내려는 내용은 성능 통계이고 전부 차단된다. 종단 테스트는 이 차단만 예상된 위반으로 분리해 확인한다.
- 모델은 **얼굴 윤곽을 처음 켤 때만** 불러온다. 끈 상태로 쓰는 사람은 16MB를 내려받지 않는다.

## 5. 화면 동작

**켜기·끄기**
- 설정 창에 체크박스 **"얼굴 윤곽 표시 (시연용)"**. **기본은 끔.** `localStorage` 키 `pose.face`.
- 켜면 모델을 불러오고(첫 한 번, "얼굴 모델 불러오는 중" 안내), 이후 계산한다.
- 불러오기는 **약속(promise) 하나만** 둔다. 켜기·끄기를 빠르게 반복해도 모델이 두 번 만들어지지 않게, 카메라와 같은 방식으로 **요청 번호**를 매겨 마지막 요청만 살린다. 끈 뒤에 불러오기가 끝나면 만든 모델을 바로 닫는다.
- 불러오기에 **30초 시간 제한**을 둔다 (LTE에서 16MB). 넘거나 실패하면 안내문을 띄우고 얼굴 기능만 끈다 (체크박스도 끔으로 되돌림).
- 끄면 `close()`로 모델을 닫아 GPU 메모리를 푼다. 파일은 브라우저 캐시에 남아 다시 켤 때 부담이 작다.
- 계산 중 예외(아이폰이 앱 전환 뒤 WebGL 컨텍스트를 잃는 경우 등)가 나면 **한 번은 모델을 다시 만든다.** 또 실패하면 안내문을 띄우고 끈다.

**계산 시점 (메인 스레드 부담 줄이기)**
- `detectForVideo`는 동기 함수라 도는 동안 프레임 캡처·전송·그리기가 모두 기다린다. 그래서:
  - **새 영상 프레임일 때만** 계산한다. `video.requestVideoFrameCallback`을 쓰고, 지원하지 않으면 `requestAnimationFrame`에서 `video.currentTime`이 바뀌었는지 본다.
  - 초당 계산 **상한 15회**. 표시용이라 충분하다.
  - 느린 폰에서 뼈대 fps가 크게 떨어지면 Web Worker로 옮기는 것을 검토한다 (이번 범위 밖, 7장 실측으로 판단).
- VIDEO 모드의 시간값은 두 표시 방식 모두 `performance.now()` 하나로 넣는다 (계속 늘어나야 한다).
- 탭이 가려지면 계산을 멈추고, 돌아오면 다시 한다.

**계산 대상 (표시 방식을 따른다 — 뼈대와 같은 프레임에 겹치도록)**
- **실시간 표시**: 화면의 카메라 영상(원본 해상도)을 위 규칙대로 계산한다. 윤곽은 영상에 바로 따라붙는다 (뼈대는 서버 왕복만큼 늦는다는 기존 안내 유지).
- **동기 표시**: 프레임을 보낼 때(`pump`) 영상을 **원본 크기 캔버스에 한 번 그리고, 거기서 640 전송 이미지를 만든다.** 두 프레임이 같은 순간이 된다. 얼굴은 보낸 직후, 서버 응답을 기다리는 동안 원본 크기 프레임으로 계산해 `seq`와 함께 보관하고, 응답이 오면 뼈대와 같이 그린다. 서버가 끊기면 동기 표시의 윤곽도 멈춘다 (의도된 동작).

**그리기**
- `draw()` 순서: 지우기 → (동기면 보낸 프레임) → 뼈대(결과가 있으면) → 윤곽(있으면). **윤곽은 뼈대 결과와 분리한다** — 실시간 표시에서는 서버 연결 전·재연결 중에도 윤곽이 나온다. 얼굴 계산이 끝날 때도 `draw()`를 부른다.
- 얼굴마다 36점을 이은 **분홍(`COLORS.face`) 닫힌 선**, 두께 2px. 좌우 반전·레터박스는 뼈대와 같은 좌표 변환(`fitContain`)을 쓴다. 좌표를 0~1로 자르지 않는다 (화면 밖은 캔버스가 잘라 윤곽이 납작해지지 않음).
- 상단 표시줄에 **얼굴 수** (`#faces`). 꺼져 있으면 `-`. 통계 초기화(`resetStats`) 때도 `-`.
- `lib.js`에 `faceOutline(landmarks, rect) -> [[x, y], …]` (MediaPipe 결과인 `{x, y, z}` 객체 478개에서 윤곽 36점을 순서대로 뽑아 화면 좌표로) 순수 함수를 두고 테스트한다.

## 6. 사생활

- 얼굴 윤곽 좌표는 사람을 알아보는 데 쓰일 수 있는 정보에 가깝다.
- **기기 안에서만 계산하고, 서버로 보내지 않으며, 저장하지 않는다.** 478점 중 윤곽 36점의 [x, y]만 남기고 나머지 점과 깊이(z)는 계산 직후 버린다 (`face.js` → `pickOutline`).
- 기본은 꺼 두고 시연할 때만 켠다.
- 넘어짐 판단 등 이후 기능은 얼굴 윤곽을 입력으로 쓰지 않는다. 심사·발표에서는 "시연용 표시 기능"으로만 소개한다.
- (참고) 영상 자체는 기존 개발용 구조대로 서버로 전송된다. 이 기능이 그 사실을 바꾸지는 않는다.

## 7. 테스트

자동
- Node: `faceOutline` — `{x, y, z}` 478개 입력에서 36점을 정해진 순서로 뽑는지, 화면 좌표 변환, 점이 모자라면 빈 배열.
- 브라우저 종단 (기존 8단계 유지, 단계 추가). 헤드리스 Chrome은 CPU 경로로 돌 가능성이 크다 — 자동 테스트는 CPU 경로를 확인한다.
  - **CSP 위반 수집**: 페이지의 `securitypolicyviolation` 이벤트와 콘솔 오류를 모아, 하나라도 있으면 실패 (`pageerror`만으로는 CSP 위반을 못 잡는다).
  - 기본 끔: `#faces`가 `-`이고 `vendor/mediapipe` 파일을 요청하지 않음.
  - 가짜 카메라를 `zidane.jpg`(1280×720, 가까이 찍힌 2명)로 한 브라우저를 따로 띄워 켬 → `#faces` 1 이상, 스크린샷으로 윤곽이 얼굴에 겹치는지 확인. 동기 표시에서도 윤곽이 그려짐. 끄면 `#faces`가 `-`.
  - **멀리 있는 얼굴 흉내**: 사진을 1/2·1/3 크기로 줄여 1280×720 검은 바탕 가운데에 둔 영상으로 어느 크기까지 잡히는지 기록한다 (합격 기준이 아니라 기록).
  - 켜기·끄기를 빠르게 반복해도 오류 없이 마지막 상태를 따름.
  - 서버 연결 없이(설정만 하고 서버 꺼 둠) 실시간 표시에서 윤곽이 나옴.

수동 (폰·노트북, 사용자)
- **거리별 인식 여부**: 0.5 / 1 / 2m에서 윤곽이 나오는지, **가까이서 잡은 뒤 뒤로 물러났을 때** 어디까지 유지되는지 실측해 README에 적는다.
- **뼈대 fps**(서버 왕복)를 얼굴 윤곽 켬/끔에서 비교, 폰 발열.
- 아이폰 Safari: `'wasm-unsafe-eval'` 허용 여부, 다른 앱에 갔다 왔을 때 윤곽이 다시 나오는지.
- GPU 경로(실기기).

## 8. 반영 절차

- 구현·테스트 후 `main`에 push한다 (Pages 반영 1~2분). **서버는 다시 시작할 필요 없다.**
- 기반 설계 문서 6장(프런트)에 이 기능을 한 줄로 요약해 둔다.

### 2차 검토 (`2026-09-30-face-outline-design-review-2.md`)

모든 항목을 반영했다.

- **9.1 탐지 거리 정정**: 1차 검토 2.1의 전제(640으로 줄여서 얼굴이 작아진다)를 확인하지 않고 받아들여 브라우저 계산의 근거로 썼던 것을 바로잡았다. 탐지 거리는 화면 속 얼굴 비율로 정해지고, 원본 해상도의 이득은 윤곽 정밀도다 (3장 표, 4장). "640 축소 영상" 테스트는 거리를 시험하지 못해 "작게 배치한 영상"으로 바꾸고, 물러나기 실측을 더했다 (7장).
- **9.2 CSP**: `connect-src 'self'` 추가, CSP 위반 수집 테스트, 아이폰 확인 (4장, 7장).
- **9.3 메인 스레드**: 새 프레임일 때만, 초당 15회 상한, 뼈대 fps 비교 (5장, 7장). 3장 표의 "뼈대에 영향 없음"도 속도에 대해서는 고쳤다.
- **10.1~10.6, 11**: 5장(그리기 분리, 동기 표시 프레임·계산 시점, 켜기/끄기 경쟁·시간 제한·close, GPU→CPU와 재생성, `resetStats`), 4장(SIMD 확인·경로 고정, 라이선스, `.gitattributes`), 7장(`{x, y, z}` 입력, CPU 경로).
