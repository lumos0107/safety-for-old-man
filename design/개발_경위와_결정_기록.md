# 개발 경위와 결정 기록 — 웹 카메라 자세 인식 시제품

작성 2026-09-30 · 팀 눈길손길 (창의융합 캡스톤디자인)

이 문서는 **왜 이 시제품을 이런 구조로 만들었는지**를 처음 이 저장소를 보는 팀원과 지도교수님이 따라올 수 있게 순서대로 적은 기록이다.
세부 규격은 설계 문서(`2026-09-29-web-pose-design.md`), 작업 순서는 구현 계획(`2026-09-29-web-pose-plan.md`)에 있다.

---

## 1. 시작: 계획서의 첫 비전 단계를 직접 돌려 보기

과제 계획서는 "자세 추정(YOLO-Pose 계열)으로 관절 좌표를 뽑고, 규칙으로 넘어짐·휘청임을 판단"한다고 적었다.
그 첫걸음으로 **카메라 영상에서 사람을 찾고 관절 17개를 실시간으로 뽑을 수 있는지, 속도가 얼마나 나오는지**부터 확인하기로 했다.

- 처음에는 파일 하나짜리 시험 스크립트(`tools/webcam_pose.py`)로 웹캠에 YOLO11n-pose를 돌렸다.
- **파이썬 가상환경(`.venv`, 3.12)을 따로 만들었다.** PC 전역 파이썬(3.14)에 PyTorch·YOLO를 깔면 다른 프로젝트의 패키지 버전을 바꿔 깨뜨릴 수 있고, 3.14는 아직 일부 비전 라이브러리를 지원하지 않는다. 가상환경은 문제가 생기면 폴더만 지우면 된다.

## 2. 문제: 개발 PC에 카메라가 없다

웹캠이라 생각한 0번 장치는 까만 화면만 보내는 **Windows 가상 카메라**였다. 사람 0명으로 나온 이유가 이것이었다.

대안을 비교했다.

| 안 | 장점 | 단점 |
|---|---|---|
| 동영상 파일로 시험 | 넘어짐 장면을 반복 시험 가능 | 실시간 시연이 안 됨 |
| 노트북으로 옮기기 | 웹캠이 있음 | GPU가 없어 느림, 환경을 다시 설치 |
| **PC는 계산(서버), 폰·노트북은 카메라만** | PC의 GPU를 그대로 쓰고, 기기마다 설치가 필요 없음 | 영상을 네트워크로 보내야 함 |

팀장이 세 번째 안을 제안했고, 계획서의 "카메라 → 계산 장치 → 판단" 흐름과도 닮아 이것으로 정했다.

## 3. 어떻게 연결할까: 웹페이지 + PC 백엔드

"네트워크가 달라도 되는가?"가 핵심 요구였다. 폰은 LTE, PC는 학교·집 와이파이일 수 있다.

- **폰에 앱을 깔지 않도록 웹페이지로 한다.** 브라우저는 HTTPS 페이지에서만 카메라를 허용하므로, 페이지는 HTTPS로 제공되는 **GitHub Pages**에 둔다. 화면 코드를 고치면 `git push`로 바로 반영되고, 주소가 고정이며, 팀원도 같이 고칠 수 있다.
- **PC를 인터넷에 여는 방법은 Tailscale Funnel**로 정했다.
  - 공유기 포트포워딩은 학교·기숙사 네트워크에서 대부분 막혀 있다.
  - Cloudflare 임시 터널도 가능했지만, Cloudflare는 자기 서버에서 암호화를 풀기 때문에 원칙적으로 영상을 볼 수 있다. **Funnel은 이 PC에서 암호화를 풀어 중계 서버가 영상을 볼 수 없다.** 사생활을 강조하는 과제라 이 차이를 중요하게 봤다.
  - "무료 VPN이 위험하지 않나"는 질문이 있었다. Tailscale은 인터넷 통신 전체를 업체로 보내는 일반 무료 VPN과 달리, 내 기기끼리만 WireGuard로 암호화해 잇는 방식이다. 실제로 조심할 점은 로그인 계정(2단계 인증)과, Funnel 주소가 공개된다는 사실이다.
- **저장소는 공개**로 했다. 무료 GitHub Pages는 공개 저장소여야 하고, 비공개로 해도 페이지 자체는 누구나 볼 수 있다. 그래서 비밀값(토큰)·실제 서버 주소·영상·개인정보는 저장소에 넣지 않는 것을 원칙으로 했다.

> 이 구조는 **개발용**이다. 원본 영상을 네트워크로 보내므로 계획서의 "엣지 처리·원본 영상 미전송" 원칙과 다르다. 최종 시스템(라즈베리파이 엣지)으로 소개하지 않는다.

## 4. 설계 → 검토 → 계획 → 검토 → 구현

파일 하나짜리 시험이 "웹 화면 + PC 서버 + 터널"로 커졌기 때문에, 바로 코딩하지 않고 **설계 문서부터 썼다.**
설계는 외부 검토를 두 번 받았고, 구현 계획도 한 번 검토를 받았다. 검토 의견은 항목마다 사실인지 확인한 뒤 반영했고, 다르게 반영한 것은 이유를 문서 끝 "반영 기록"에 남겼다.

검토에서 나와 구조를 바꾼 주요 결정:

| 결정 | 이유 |
|---|---|
| 방어선은 **긴 토큰 하나** (43자 이상, 짧으면 서버가 시작을 거부) | Funnel 주소는 인증서 공개 기록으로 누구나 찾을 수 있어 "주소를 모르면 못 들어온다"가 성립하지 않는다 |
| 서버는 `127.0.0.1`에만 열고 Funnel로만 들어오게 | 같은 네트워크의 다른 기기가 직접 붙지 못하게 |
| FastAPI 문서 페이지(`/docs`) 끄기 | Funnel이 모든 경로를 공개하므로 |
| **새로 인증한 연결이 이전 연결을 대체** (거부하지 않음) | 폰 와이파이가 끊겼다 붙을 때, 서버가 아직 살아 있다고 여기는 이전 연결 때문에 재접속이 막히는 것을 피하려고 |
| 밀려난 쪽은 **재연결하지 않음** | 폰과 노트북을 동시에 켜면 두 탭이 서로 연결을 뺏으며 무한 반복하므로 |
| 밀려난 대기 연결은 활성이 될 수 없음 | 닫히기 직전에 받은 인증 메시지로 뒤늦게 인증해 정상 사용자를 끊는 경쟁 상태가 있었다 |
| **추론은 전용 스레드 하나에서만** | 연결이 대체되는 순간 이전·새 연결의 추론이 겹칠 수 있고, YOLO 모델은 동시 호출에 안전하지 않다 |
| 한 장 보내고 결과를 받은 뒤 다음 장 | 네트워크가 느려도 지연이 쌓이지 않고 속도만 떨어진다 |
| 응답 5초·연결 8초 제한 후 재연결 | 와이파이↔LTE 전환이나 인터넷이 안 되는 와이파이에서 화면이 멈추지 않게 |
| 크기 제한 2단계 + 디코딩 전 해상도 확인 | 작은 파일에 거대한 해상도를 적은 "이미지 폭탄"이 메모리를 터뜨리지 않게 |
| 암호화 안 된 주소(`http`/`ws`)는 이 PC 안에서만 허용 | 토큰이 평문으로 외부에 나가지 않게 |
| 실행 스크립트가 Funnel을 켜고, Ctrl+C로 끌 때 같이 끔 | Funnel은 쓸 때만 열어 둔다 |
| 좌표를 0~1 비율 + 원본 크기 + 프레임 번호로 보냄 | 다음 단계(넘어짐 판단)에서 몸 기울기를 계산하고 시간 순서로 분석하려면 필요하다 |

## 5. 구현과 확인

- 11단계로 나눠 **각 단계마다 실패하는 테스트를 먼저 쓰고** 통과시켰다.
  - 서버 테스트 60개 (실제 GPU 모델과 실제 서버 실행 포함)
  - 화면 계산 함수 테스트
  - 브라우저 종단 검증: 카메라가 없으므로 **예시 사진을 Chrome의 가짜 카메라로 넣어** 연결·인식·재연결·연결 대체·틀린 토큰을 자동으로 확인
- 구현 중 계획과 다르게 한 것은 모두 이유와 함께 기록했다 (예: Windows에서 한글 출력이 깨지는 테스트 수정, 최신 라이브러리 경고 대응).
- 마지막에 **새 검토자가 전체 코드를 한 번 검토**했다. 폰에서 처음 부딪힐 문제 3개를 찾았고, 각각 실패하는 테스트를 먼저 만든 뒤 고쳤다.
  - 폰 키보드의 "이동"을 누르면 설정이 저장되지 않고 취소됨
  - "시작"을 두 번 누르면 카메라가 새고 같은 기기가 스스로 연결을 빼앗김
  - 응답 없는 네트워크에서 "연결 중"에 몇 분씩 머묾
- 공개 저장소에 올리기 전에 토큰·실제 서버 주소가 파일과 git 기록 어디에도 없음을 검사했다. 설계 문서에 주소가 들어간 커밋이 있었는데, 아직 올리기 전이라 기록에서 지웠다.
- `main`에 올리고 Pages 반영, Funnel 외부 경로(인증, 인식, 다른 사이트·틀린 토큰 차단)를 확인했다.

## 6. 폰 시험 이후

- 실제 폰으로 접속해 동작을 확인했다.
- **관절 점을 부위별 색으로 구분**했다: 얼굴 분홍, 몸통 노랑, 왼쪽 파랑, 오른쪽 주황. 다음 단계에서 넘어짐 판단의 기준이 될 어깨·골반과 좌우가 한눈에 보이게 하려는 것이다.
- **얼굴 윤곽 표시**를 설계했다 (`2026-09-30-face-outline-design.md`). 자세 모델은 얼굴 5점만 주므로 얼굴 전용 모델이 필요하다.
  - **목적:** 시연할 때 인식이 사람에게 제대로 붙어 있는지 한눈에 보여 주기 위한 **표시 기능**이다. 넘어짐 판단에는 쓰지 않는다.
  - 처음에는 PC 서버에서 계산하도록 설계했으나, 검토 후 **폰·노트북 브라우저에서 계산**하기로 바꿨다. 카메라 원본 해상도로 계산해 더 먼 거리의 얼굴을 잡을 수 있고, 서버·통신 규격을 바꾸지 않으며, 얼굴 정보가 서버로 가지 않는다. 대신 카메라 기기가 계산을 맡는다.
  - 얼굴 정보는 민감하므로 **기본은 끔**, 켜도 기기 안에서만 계산하고 저장하지 않는다.

## 7. 아직 남은 것

- 폰 시험에서 확인할 것: 다른 앱을 쓰다 돌아왔을 때 영상이 굳지 않는지(특히 아이폰), 화면 회전, 와이파이↔LTE 전환.
- 최종 검토에서 미뤄 둔 사소한 문제 8개 (회전 직후 동기 표시 비율, 재연결 직후 fps 표시 등).
- 얼굴 윤곽을 구현한 뒤 확인할 것: 거리별(0.5 / 1 / 2m) 인식 여부, 켬/끔에 따른 fps와 폰 발열. 구현 후 5장의 테스트 개수도 고친다.
- 다음 큰 단계: 이 관절 좌표로 **넘어짐·휘청임 판단 규칙**을 만드는 것 (계획서의 규칙 기반 지표).
